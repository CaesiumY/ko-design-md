# 직접 다시 잰 값

푼 쪽의 자기 보고가 아니라, 문제를 푼 가지에서 git 과 명령으로 다시 잰 값이다. 사실만 적는다.
푼 쪽의 기록과 이 문서가 어긋나면 이 문서를 따른다. 이 문서의 수는 2026-11-25 에 가지 `eval/*` 열여덟 개의 끝 커밋에서 잰 기록이다.

## 0. 어떻게 풀리고 어떻게 쟀나

- 푼 쪽은 아홉이다. 구조마다 문제 5, 1, 2, 3 을 이 순서로 푼 에이전트 하나와, 문제 4 를 따로 푼 에이전트 둘(a, b).
  아홉 모두 같은 모델이고 같은 지시 파일(`briefs/solver-common.md`, 문제 4 는 `briefs/solver-s4.md` 도)을 받았다.
  구조마다 달리 준 것은 구조 이름, 시작 커밋, 안내 문서의 경로 셋뿐이다.
- 문제마다 구조의 시작 커밋에서 새 가지를 쳤다. 다만 문제 5, 1, 2, 3 은 한 에이전트가 이어 풀어서 앞 문제에서 읽은 것을 기억한다.
  문제 5(원본 찾기)를 맨 먼저 풀린 것은 그 때문이다.
- 줄 수는 `git diff --numstat <시작> <가지 끝>` 에서 결과 기록 파일을 빼고, 파일의 역할로 나눠 셌다(1절).
- 요구가 서빙 파일에 들어갔는지는 가지의 서빙 파일을 `git show` 로 읽어 셌다(2절).
- 검사와 시간은 확인용 에이전트 하나가 작업 폴더 하나에서 가지를 차례로 체크아웃해, 정해진 스크립트로 한 번씩 돌렸다(3절, 4절).
  다른 작업과 겹치지 않게 차례로 돌렸고 PC 한 대의 값이다.
- 도구 호출 수와 걸린 시간은 실행 도구가 에이전트가 끝날 때 찍어 준 값이다(5절). 이 값은 여러 에이전트가 함께 돌던 때의 것이다.

역할의 뜻:

- 원본: 사람이 고치는 항목 파일. html-frame 은 서빙 파일 자체, fragments 는 `preview-src/`, components 는 `entries/`.
- 공용: 모든 항목이 함께 쓰는 것. 틀 스타일(`frame.css`), 조립기와 부품, 약속 검사, 뼈대 파일.
- 산출물: 명령이 원본에서 만들어 내는 서빙 파일. html-frame 에는 없다.
- 안내: 구조의 `README.md`, `STATS.md`. 테스트: 구조의 테스트 파일.

## 3. 검사를 다시 돌린 결과 (가지 열여덟 개)

- 열여덟 가지 모두 약속 검사, `pnpm validate:previews --slug …`, 구조의 테스트 파일이 종료 값 0 으로 끝났다.
- fragments 와 components 는 조립(빌드) 명령을 다시 돌린 뒤 `git status` 가 비어 있었다. 커밋된 서빙 파일이 원본에서 만든 것과 같다는 뜻이다.
- 브라우저로 그려서 보는 확인(화면 비교, 대비 측정, 넘침)은 이 재확인에 없다. 푼 쪽도 문제 4 에서 하지 않았다고 적었다.
- `pnpm gates`(CI 와 같은 검사 묶음 전체)는 어느 가지에서도 돌리지 않았다.

### 일부러 넣은 잘못을 약속 검사가 잡았나

재확인에서는 세 구조 모두 **서빙되는 토스 파일**에 같은 잘못을 넣었다.

| 문제 | 넣은 잘못 | html-frame | fragments | components |
| --- | --- | --- | --- | --- |
| 3 | 선택 구역과 입력 구역을 뒤바꿈 | 종료 값 1. `preview.html:1844 [zone-order] 구역 "selection" 가 구역 "inputs" 뒤에 있다` + 고치는 법(구역을 통째로 앞으로 옮긴다) | 종료 값 1. 두 건: `1829줄부터 원본에서 조립한 결과와 다르다`, `1931 구역 순서가 틀렸다 … 순서는 zones.ts 의 목록이 정한다` + `pnpm previews:build toss` | 종료 값 1. 두 건: `1930 [selection] 구역 순서가 틀렸다 … (kit/zones.ts)`, `1828 이 entries/toss 를 빌드한 결과와 다르다 … 원본 줄은 pnpm pv:where toss 1828` |
| 2 | 버튼 구역 첫 칸의 `aria-labelledby` 를 지움 | 종료 값 1. `preview.html:1681 [cell-group] 칸 "button-size" 에 aria-labelledby 가 없다` + 고치는 법(이 줄의 칸 태그에 `aria-labelledby="pv-label-button-size"` 를 단다) | 종료 값 1. 두 건: `1768줄부터 원본에서 조립한 결과와 다르다`, `1768 칸 button-size 의 aria-labelledby 가 "pv-label-button-size" 가 아니다(지금: 없음). 칸과 이름표의 마크업은 조립기(assemble.ts 의 칸 반복문)가 쓴다` + `pnpm previews:build toss` | 종료 값 1. 두 건: `1767 [buttons/button-size] … aria-labelledby 가 "(없음)" 다 … 이 속성은 틀(kit/parts.ts 의 renderCell)이 쓴다`, `1767 이 entries/toss 를 빌드한 결과와 다르다 … 원본 줄은 pnpm pv:where toss 1767` |

- fragments 와 components 의 푼 쪽은 이 두 잘못을 원본에는 넣을 수 없었다고 적었다. 칸의 속성과 구역의 순서를 항목의 원본이 아니라 공용 코드가 쓰기 때문이다. 그래서 두 구조의 검사는 같은 잘못을 규칙 위반과 "원본과 서빙 파일의 어긋남" 두 가지로 짚는다.
- html-frame 은 서빙 파일이 곧 원본이라, 짚은 줄이 고칠 줄이다.
- 재확인 스크립트의 첫 실행은 문제 2 에서 칸이 아니라 구역(`<section>`)의 `aria-labelledby="pv-buttons"` 를 지웠다. 세 구조 모두 종료 값 1 로 막았다(html-frame `[zone-shape]`, fragments 와 components 는 구역 제목 규칙과 어긋남). 위 표의 문제 2 줄은 스크립트를 고쳐 다시 돌린 값이다.

## 4. 한 번 확인하는 데 걸린 시간 (ms, 가지 열여덟 개에서 한 번씩 잰 값의 범위)

| 명령 | html-frame | fragments | components |
| --- | --- | --- | --- |
| 조립(빌드) | 없음 | 499~672 | 539~593 |
| 약속 검사 | 1605~3805 | 527~606 | 512~598 |
| `validate:previews` 한 슬러그 | 1741~2920 | 1777~2094 | 1795~2080 |
| 구조의 테스트 파일 | 13223~14854 | 11848~12316 | 11886~12362 |

- html-frame 의 약속 검사는 `pnpm exec tsx <파일> <슬러그…>` 로, 나머지 둘은 `package.json` 에 이어 둔 명령(`pnpm previews:check`, `pnpm pv:check`)으로 돌렸다. 부르는 방식이 다르다.
- html-frame 여섯 가지를 먼저 쟀다. 그 첫 가지에서 패키지를 새로 설치했고, 뒤의 두 구조는 설치가 "이미 최신"이었다.
  문제 2 의 세 가지는 나중에 한 번 더 쟀고(순서는 html-frame, fragments, components), 그때 약속 검사는 1822, 592, 650 이었다.
- 테스트 시간에는 이 저장소의 테스트 실행기가 끝날 때 기다리는 약 10초가 들어 있다(세 구조 공통).
- 이 값은 구조끼리의 상대 비교에만 쓴다.

## 6. 측정에 영향을 줄 수 있는 사실

- 구조를 만든 쪽 가운데 fragments 와 components 는 사용량 한도로 한 번 끊겼다가 이어서 만들었다. html-frame 은 끊기지 않았다.
- 세 구조 모두 만든 뒤에 같은 규칙의 리뷰를 두 번 받았고, 리뷰가 짚은 안내의 모자란 설명을 고쳤다. html-frame 의 안내에 구역 표가 들어간 것은 그때다.
- 문제 5, 1, 2, 3 을 한 에이전트가 이어 풀었다. fragments 의 문제 3 기록에는 "문제 2 에서 읽은 기억으로" 테스트를 미리 찾았다는 문장이 있다.
- html-frame 의 문제 4 두 풀이는 같은 곳에서 한 번씩 실패했다(뼈대를 복사할 폴더가 없었다). a 는 그것을 "안내", b 는 "내 실수"로 적었다. 같은 일이다.
- 문제 4 의 여섯 풀이 모두 칸 안쪽의 꼴(상태 이름표, "직접 입력" 줄, 히어로 감싸개, `--primary` 같은 별칭 변수)을 치지직의 원본에서 따라 했다고 적었다. 세 구조의 안내와 기준 요약이 모두 말하지 않는 부분이다.
- 다크에서 이름표를 통째로 바꿔 끼는 것은 공용 스크립트(`iframe.js`)의 동작이다. 문제 2 에서 바꿔 낄 이름표에도 id 를 달아야 하는 것은 세 구조에 똑같이 걸렸고 세 푼 쪽 모두 달았다.
- 커스텀 태그 구조는 치지직 하나만 옮기는 짧은 시험이었고 이 시험 문제를 풀지 않았다. 기록은 그 구조의 브랜치(`46ccd564`)의 `prototypes/preview-structure/custom-tags/` 에 있다.
