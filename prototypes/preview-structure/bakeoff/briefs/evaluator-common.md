# 평가하는 쪽의 공통 지시

ko-design-md 저장소는 브랜드마다 프리뷰(그 브랜드의 디자인을 보여 주는 HTML 한 장)를 둔다. 프리뷰를 **쓰는 구조** 셋을 같은 두 항목(치지직, 토스)으로
만들었고, 어느 구조로 만들어도 브라우저에 보이는 화면은 같다. 그래서 겨루는 것은 화면이 아니라 "쓰고 고치기가 얼마나 쉬운가"다.

구조 셋:

- `html-frame`: 항목마다 손으로 쓴 HTML 한 장, 틀의 스타일만 공용 파일로 뽑음
- `fragments`: 구역마다 조각 파일로 쓰고 명령이 HTML 한 장으로 조립함
- `components`: 항목마다 모듈로 쓰고 공용 부품이 HTML 한 장으로 그려 냄

구조마다 다른 에이전트가 같은 시험 문제 다섯을 풀었다. 너는 그 **산출물과 측정값만** 보고 평가한다.

## 읽는 것

너를 부른 글이 준 평가 묶음 폴더 하나만 읽는다. 그 안에:

- `SCENARIOS.md`, `STANDARD.md`: 시험 문제와 기준 요약
- `MEASURED.md`: 문제를 푼 가지에서 git 과 명령으로 직접 다시 잰 값(구조와 문제의 표), 재는 데 쓴 방법, 측정에 영향을 줄 수 있는 사실
- `{구조}/README.md`, `{구조}/STATS.md`: 만든 쪽이 낸 안내와 정적 수치
- `{구조}/results/*.md`: 푼 쪽이 문제마다 적은 기록
- `{구조}/patches/*.patch`: 문제마다 풀이의 diff
- `custom-tags/`: 넷째 구조(커스텀 태그)의 시험이 멈춘 지점의 기록. 순위에는 넣지 않는다

읽지 않는 것: 평가 묶음 밖의 모든 것. 저장소의 다른 폴더, 다른 작업 폴더, git 이력, GitHub, 사용자 홈의 `.claude/`(메모리, 계획 파일).
서브에이전트를 띄우지 않는다. 파일을 고치지 않는다(읽기만 한다).

## 지킬 것

- 근거는 평가 묶음 안의 파일과 줄을 짚어 댄다. 묶음에 없는 것은 "묶음에 없음"이라고 쓴다. 짐작으로 채우지 않는다.
- 푼 쪽의 기록과 `MEASURED.md` 가 어긋나면 `MEASURED.md` 를 따르고 어긋남을 적는다.
- 시간과 대비 수치는 한 대의 PC 에서 잰 값이라 구조끼리의 상대 비교에만 쓴다.
- 문제 4 는 구조마다 두 번 풀렸다. 한 번의 횟수는 우연에 흔들리므로 횟수보다 **실패의 종류**(무엇을 몰라서, 어느 단계에서)를 본다.
  DESIGN.md 를 화면으로 옮기다 생긴 실패(md 해석)는 구조의 탓으로 세지 않는다.
- 안내 문서가 모자라서 생긴 일과 구조의 성질에서 온 일을 가른다. 앞의 것은 문서를 고치면 사라지고 뒤의 것은 남는다.
- **종합 순위를 내지 않는다.** 어느 구조를 고르라는 추천도 하지 않는다. 고르는 것은 사람이다.
