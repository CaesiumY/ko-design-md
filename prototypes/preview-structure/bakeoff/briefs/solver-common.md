# 시험 문제를 푸는 쪽의 공통 지시

이 저장소(ko-design-md)에서 "프리뷰를 쓰는 구조" 하나의 시험 문제를 푼다. 너는 이 구조를 만든 쪽이 아니고,
구조의 안내 문서와 이 작업 폴더의 파일만 보고 일한다. 정답표는 없다. **네가 실제로 겪은 일을 사실대로 적은 기록**이 결과물이다.

아래에서 `{구조}`, `{끝}`, `{안내}` 는 너를 부른 글이 준 값으로 바꿔 읽는다.

## 1. 시작

1. 지금 폴더가 네 전용 작업 폴더(git worktree)다. `git status` 와 `git rev-parse HEAD` 로 확인한다.
2. 첫 문제의 가지를 친다(가지 이름은 너를 부른 글에 있다). 예: `git switch -c eval/{구조}-s5 {끝}`
3. `pnpm install` 을 돌린다. 패키지 매니저는 pnpm 만 쓴다(npm 금지).
4. 아무것도 고치지 않은 상태에서 `{안내}` 가 말하는 약속 검사와 `pnpm validate:previews --slug toss`,
   `pnpm validate:previews --slug chzzk` 를 한 번씩 돌려 막힘이 없는지 본다.
   **여기서 막히면 문제를 풀지 말고 그 출력을 보고하고 끝낸다.**

## 2. 읽는 것

- 시험 문제: `prototypes/preview-structure/SCENARIOS.md` (공통 규칙과 "풀었다" 조건이 여기 있다)
- 기준 요약: `prototypes/preview-structure/STANDARD.md`
- 구조 안내: `{안내}`
- 그 밖에 이 작업 폴더 안의 파일은 읽어도 된다.

읽지 않는 것:

- 다른 작업 폴더(`.claude/worktrees/` 의 다른 폴더, 저장소의 원래 폴더).
- 다른 브랜치와 git 이력. `git log`, `git show`, `git diff`, `git stash` 는 `{끝}` 과 네가 친 가지에만 쓴다. `eval/` 로 시작하는 남의 가지를 보지 않는다.
- GitHub 이슈와 PR, 배포된 사이트.
- 사용자 홈의 `.claude/` 폴더(메모리, 계획 파일)와, 이 지시 파일을 뺀 임시 폴더의 다른 파일.
- 이 작업 폴더의 `.claude/cache/` 는 네가 쓴 커밋 메시지 파일을 두는 데만 쓴다.

서브에이전트를 띄우지 않는다.

## 3. 문제마다

- 문제마다 `{끝}` 에서 새 가지를 친다: `git switch -c eval/{구조}-s{번호} {끝}`. 앞 문제의 결과를 물려받지 않는다.
- 푼 것을 커밋한다(**풀이 커밋**). 그 다음 결과 파일을 **따로** 커밋한다(**결과 커밋**).
  줄 수는 풀이 커밋까지만 센다: `git diff --stat {끝} <풀이 커밋>`.
- 문제 2, 3 의 "일부러 넣는 잘못"은 풀이 커밋 **뒤에** 넣는다. 약속 검사의 출력을 결과 파일에 옮겨 적고 `git restore` 로 되돌린다.
  잘못은 커밋하지 않는다.
- 다음 문제로 넘어가기 전에 `git status` 가 깨끗한지 본다.
- 고치지 않는 파일: `prototypes/preview-structure/SCENARIOS.md`, `STANDARD.md`, `dom-diff.ts`, `base-notes/`,
  `services/`, `.claude/skills/`, `.claude/agents/`, `.claude/rules/`, `src/lib/preview-validator.ts` 와 그 밖의 기존 검증기.
  구조가 제 것으로 가진 약속 검사와 그 테스트는 문제가 청하면 고친다.

## 4. 결과 파일

경로는 `prototypes/preview-structure/results/{구조}-s{번호}.md`. SCENARIOS.md 가 청한 항목을 적고, 덧붙여 아래를 지킨다.

- **명령 기록**: 끝에 되짚어 쓰지 말고 실행할 때마다 한 줄씩 적는다. 명령, 성공인지 실패인지, 실패면 출력 한 줄과 종류.
- **실패의 종류**는 넷 중 하나로 적는다.
  - 구조: 이 구조의 성질 때문에 생긴 것
  - 안내: 안내 문서가 말하지 않았거나 틀리게 말해서 생긴 것
  - 환경: 아래 5절의 셸 제약, 설치, Windows 때문에 생긴 것
  - 내 실수: 오타나 잘못 읽음
- **파일 수와 줄 수**는 셋으로 나눠 적는다: 손으로 고친 원본 / 명령이 만들어 낸 산출물 / 안내 문서와 테스트.
- **걸린 시간**은 명령이 스스로 찍은 값만 적는다. 찍지 않으면 "재지 않음"이라고 적는다(시간은 뒤에 따로 잰다).
- **막히거나 헷갈린 곳**마다: 무엇을 찾으려 했고, 어디를 봤고, 어디서 답을 얻었는지. 파일을 몇 개 열어 봤는지.
- 평가, 추천, 다른 구조와의 비교는 적지 않는다. 겪은 일만 적는다.

## 5. 셸 제약 (지키지 않으면 명령이 거부된다)

- Bash 명령은 한 번에 하나, 단순하게 쓴다. 파이프(`|`), 리다이렉트(`>`), 체인(`&&`, `;`), heredoc, `cd` 를 쓰지 않는다.
- 파일은 Write, Edit 도구로 쓴다. 스크립트가 필요하면 파일로 써서 `node <경로>` 나 `pnpm exec tsx <경로>` 로 돌린다.
- 커밋: 메시지를 이 작업 폴더의 `.claude/cache/` 아래 파일에 Write 로 쓰고 `git commit -s -q -F <그 파일>` 로 커밋한다.
  메시지는 한국어이고 첫 줄은 `eval({구조}): 문제 N …` 꼴이다.
  도구나 AI 의 서명 줄(`Co-Authored-By`, `Generated with` 등)을 넣지 않는다. `-s` 가 붙이는 `Signed-off-by` 한 줄만 남는다.
- 푸시, PR, 이슈 댓글을 하지 않는다. 로컬 커밋만 한다.

## 6. 끝 보고 (짧게)

문제마다 한 줄씩: 가지 이름, 풀이 커밋과 결과 커밋의 해시, "풀었다" 조건 셋을 각각 채웠는지, 일부러 넣은 잘못을 검사가 잡았는지.
그리고 풀지 못했거나 건너뛴 것. 의견은 넣지 않는다.
