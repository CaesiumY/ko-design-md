## 관점
새 항목의 프리뷰를 DESIGN.md 와 구조 안내만 받고 처음부터 쓰고, 검사 메시지를 보고 고치기를 되풀이하는 에이전트의 눈.

## 기준별 평가

**A. 처음 쓸 때 새로 알아야 하는 문법**
- html-frame: 평범한 HTML 에 규칙 둘(틀 링크 자리, `--pv-*` 변수)만 더하면 된다. 대신 구역과 칸의 겉 태그, 세 곳에 같은 id 를 손으로 쓴다(html-frame/README.md 79줄, 92~97줄).
- fragments: 줄 단위의 전용 문법이다. `<pv-cell>` 은 줄 머리에 두고, 이름표는 한 줄, 시연은 두 칸 넘게 들여 쓴다(fragments/README.md 47~57줄). CSS 를 몇 칸 들여 쓸지는 안내에 없어서 치지직을 보고 따랐다(fragments-s4a 99줄, s4b 95줄).
- components: TS 모듈, 템플릿 리터럴의 이스케이프 규칙, `#preview-kit`, 타입 검사, prettier 단계를 알아야 한다(components/README.md 81~85줄, 6절).

**B. s4 에서 헛돈 곳(실패의 종류)**
| 구조 | a | b |
| --- | --- | --- |
| html-frame | 폴더가 없어 `cp` 실패(안내 탓) | 같은 실패. 푼 쪽은 "내 실수"로 적었지만 MEASURED 152줄은 같은 일로 본다 |
| fragments | 조립 전에 검사해서 "서빙 파일 없음"(구조 탓, 안내가 미리 말함) | 같음 |
| components | 0 | 0 |

여섯 풀이 모두 실제 약속 위반으로는 한 번도 막히지 않았다. 여섯 모두 안내에 없는 칸 안쪽 꼴을 치지직에서 베꼈다(MEASURED 153줄). 이것은 세 구조 공통의 안내 공백이다. 다크 시트에 값을 글자로 쓸지 참조로 쓸지도 셋 모두 안내에 없었다(fragments-s4a 100줄, components-s4a 76줄).

**C. 틀렸을 때 메시지가 고칠 곳을 가리키나** (MEASURED 3절, 일부러 넣은 잘못 기준)
- html-frame: 한 건이 나온다. 짚은 줄이 곧 고칠 줄이고, 달 속성의 글자까지 알려 준다(html-frame-s2 26~27줄).
- fragments: 두 건이 나온다(어긋남, 규칙 위반). 어긋난 상태에서는 원본 줄로 옮겨 주지 않는다(fragments-s2 55줄).
- components: 두 건이 나온다. 어긋남 메시지가 "항목 모듈을 고치고"라고 하는데, 이 경우에는 모듈에 고칠 것이 없다(components-s2 36줄). 문서를 고치면 사라질 종류다.
- 원본 쪽 잘못(fragments 의 조각 꼴 위반, components 의 타입 오류)에 대한 메시지는 이 시험에서 한 번도 나오지 않았다.

**D. 서빙 줄에서 원본 찾기** (s5)
- html-frame: 옮기는 명령이 0개다(html-frame-s5 13줄).
- fragments: `where` 명령 한 번으로 찾는다. 임시 폴더에서도 `--src` 로 쓸 수 있다(README 123줄).
- components: `where` 명령 한 번으로 두 줄을 다 찾았다. 하지만 온보딩의 임시 폴더에서는 이 명령을 쓸 수 없어 칸 이름으로 찾아야 한다(components/README.md 193줄).
- 헛짚은 횟수는 셋 모두 0 이다.

**E. 구조가 실수를 미리 막아 주는 정도**
- fragments, components: 칸의 속성과 구역 순서는 원본에서 틀릴 수가 없다(MEASURED 112줄).
- html-frame: 손으로 쓴 겉 태그를 검사가 잡는다. 다만 시연이 빈 뼈대 칸도 두 검사를 다 통과했다(html-frame-s4a 54줄). 틀 링크를 지워도 기존 검증기는 통과하고, 새로 만든 약속 검사만 잡는다(html-frame STATS 4절).
- components: 리터럴 안쪽 마크업은 타입 검사가 보지 않는다(components STATS 4절).

**F. 한 번 확인하는 비용** (MEASURED 4절, 상대 비교만)
- html-frame 은 약속 검사 하나가 1.6~3.8초로 가장 느리다. 부르는 방식이 달라 순수한 차이인지는 알 수 없다.
- 나머지 둘은 조립 0.5~0.7초와 약속 검사 0.5~0.6초를 더한 값이다.

## 무게별 순위

### 1. 새 항목 만들기가 단순한가
1위 html-frame, 2위와 3위는 가리지 못함(fragments, components).
- html-frame: 새로 배울 문법이 가장 적다. 유일한 실패는 안내 한 줄로 고칠 수 있다.
- 다만 측정으로는 셋이 거의 같다. 도구 호출 44~53회, 손으로 쓴 줄 221~281줄, 실제 약속 위반 0건이다.
- fragments: 실패는 미리 예고된 순서 문제 하나다.
- components: 실패는 0건이지만 단계(타입 검사, 빌드, prettier)가 가장 많다.
- 둘의 문법 함정(fragments 의 들여쓰기, components 의 이스케이프)은 어느 풀이에서도 실제로 걸리지 않아 근거로 가를 수 없다.

### 2. 한꺼번에 고치기 쉬운가
1위와 2위는 가리지 못함(fragments, components), 3위 html-frame.
- html-frame: s2 에서 114줄을 일회용 스크립트로 바꾸고 뼈대까지 고쳤다(MEASURED 54줄). s3 에서 93줄을 옮겼고, 안내에 옮겨 적은 구역 표도 고쳐야 했다.
- fragments, components: 조립기나 부품 한 곳과 목록 한 곳만 고쳤고, 항목 원본은 0줄 또는 칸 하나만 바뀌었다(MEASURED 1절).
- 둘 사이의 차이는 메시지의 문구 정도라서 가르지 못했다.

### 3. 지금 있는 검사와 온보딩 흐름을 얼마나 살리나
1위 html-frame, 2위 fragments, 3위 components.
- html-frame: 저자가 쓰는 파일이 그대로 한 장이고, 복사 단계도 그대로다. 약속 검사 한 줄만 더해진다(STATS 3절). 대가는 기존 검증기가 틀 파일을 보지 못한다는 것이다(ADR 0002 의 문장이 어긋난다).
- fragments: 조립 단계 하나가 더해진다. 임시 폴더에서도 원본 찾기 명령이 돈다. 조립에 md 의 이름이 필요해서 Stage 8 뒤에만 조립할 수 있다(README 128줄).
- components: 빌드 단계가 하나 더해지고, 복사 한 줄이 세 줄이 된다. 임시 폴더에서는 원본 찾기 명령을 쓸 수 없다. 모듈을 저장소 밖에 두면 공용 부품을 불러오지 못한다. 타입 검사, 린트, 포맷 검사에 2,593줄이 새로 들어간다(STATS 1, 3, 4절).

## 측정이 말해 주지 않는 것
- **고치기 되풀이가 재지지 않았다.** s4 의 여섯 풀이 어디서도 실제 약속 위반이나 검증기 막힘이 나지 않았다. 새 항목을 쓰는 에이전트가 메시지를 보고 고치는 과정이 한 번도 측정되지 않은 셈이다.
- **원본 쪽 잘못은 시험하지 않았다.** 일부러 넣은 잘못은 모두 서빙 파일에 넣었다. fragments 의 조각 꼴 메시지와 components 의 타입 오류 메시지는 재지 않았다.
- **온보딩 흐름을 실제로 돌리지 않았다.** `--src`, `--entry` 를 쓰는 임시 폴더 흐름과, 임시 파일의 대비 관측을 해 보지 않았다. 저자 프롬프트는 세 구조 모두 고치지 않았다.
- **브라우저 확인이 없다.** 넘침, 대비, 화면 비교를 문제 4 에서 하지 않았다(MEASURED 100줄).
- **안내만으로 쓸 수 있는지 모른다.** 여섯 풀이 모두 치지직을 베꼈다. 치지직 같은 본보기가 없을 때 안내만으로 쓸 수 있는지는 알 수 없다.
- **풀이 순서가 섞였다.** 문제 5 를 먼저 풀어 안내를 막 읽은 상태였고, fragments 의 s3 는 s2 에서 읽은 기억을 썼다(MEASURED 151줄).

## 커스텀 태그
- 기존 검사 셋이 하나도 막지 않았다. 하지만 이것은 검사기가 속성으로 옮긴 이름표와 다크 이름표를 보지 못한 결과다. 금지 문구를 이름표 속성에 심어도 통과했다(custom-tags/README.md 4.2절, 4.4절).
- 스크립트 없이 열면 구역 제목과 이름표 20줄이 사라진다(4.5절).
- 에이전트의 자리에서 보면, 검사의 "통과"가 "보고 맞았다"는 뜻이 아니라는 점이 가장 위험하다.
