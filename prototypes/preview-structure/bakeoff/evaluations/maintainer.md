## 관점
항목 29개와 공용 코드, 검사, CI 를 몇 해 돌보는 사람의 눈. 두 항목에서 잰 값이 29개, 그 너머로 늘면 어떻게 되는지를 본다.

## 기준별 평가

**1. 공통 규칙 하나를 바꿀 때 손이 항목 수만큼 늘어나나**

| 바꾸는 것 | html-frame | fragments | components |
| --- | --- | --- | --- |
| 틀 모양(문제 1) | `frame.css` 1파일. 항목 파일은 안 바뀜(MEASURED 40, 44) | `frame.css` 1파일, 다시 만든 서빙 파일이 항목 수만큼 바뀜(MEASURED 41) | fragments 와 같음(MEASURED 42) |
| 칸 태그(문제 2) | 항목 파일마다 고침. 두 항목 +114 −114 를 커밋하지 않은 일회용 스크립트로 했다(MEASURED 50, 54) | 조립기 한 곳 +8 −3, 항목 원본 0(MEASURED 51) | 부품 한 곳 +9 −4, 항목 원본 0(MEASURED 52) |
| 구역 순서(문제 3) | 목록은 1곳이지만 항목마다 `<section>` 을 옮김. 토스만 93줄, 스크립트로(MEASURED 60, 64) | 목록 1곳, 토스 원본 0 | 목록 1곳, 토스 원본 0 |

html-frame 은 틀 모양에서만 이기고, 태그와 순서는 항목 수에 비례하는 일이 된다. 그 일에 쓴 스크립트는 저장소에 남지 않았다. 29개 항목은 손으로 쓴 꼴이 제각각이라, 푼 쪽이 걸어 둔 "꼴이 다르면 멈춤"(html-frame-s2.md 17)에 걸릴 가능성이 남는다. 이것은 구조에서 오는 성질이다.

**2. 검사가 막았을 때 원인으로 가는 길**
- html-frame: 짚은 줄이 고칠 줄이다. 문제 5 에서 원본을 찾는 데 명령 0개(html-frame-s5.md 13). 메시지에 고칠 글자가 그대로 있다(MEASURED 109~110).
- fragments: 같은 잘못을 규칙 위반과 원본과의 어긋남, 두 건으로 낸다(MEASURED 109~112). 줄 찾기는 줄 대 줄 대응이라 단단하다(README 140). 다만 서빙 파일이 어긋난 상태에서는 지적이 원본 줄로 옮겨지지 않는다(fragments-s2.md 55).
- components: 두 건으로 내고, 칸 이름까지 짚는다. 하지만 문제 2 에서 어긋남 메시지가 "항목 모듈을 고치라"고 했는데 모듈에는 고칠 것이 없었다(components-s2.md 36). 줄 찾기 도구는 부품의 들여쓰기 약속에 묶여 있어서, 부품을 고치면 함께 고쳐야 한다(components/STATS.md 54, README 152).

**3. 새로 떠안는 고장 방식**
- html-frame: 틀 링크가 빠지거나 파일을 못 불러와도(404) 기존 검증기는 통과한다(html-frame/STATS.md 48~58). 틀을 바꿔도 항목의 이력과 `last_updated` 에는 흔적이 없다(같은 파일 60).
- fragments: 원본과 서빙 파일의 어긋남, 조립 실패, 조립하려면 md 의 `name` 이 있어야 함, 공통 `<head>` 때문에 바뀌는 줄(fragments/STATS.md 46~53).
- components: fragments 의 것에 더해 타입 검사, 린트, 포맷 검사가 새로 보는 줄이 2,593줄 늘고, 그중 항목 모듈이 1,302줄이다. 이 줄은 항목 수에 비례해 는다(components/STATS.md 22~24). 그 밖에 템플릿 리터럴(백틱으로 감싼 HTML 글)의 이스케이프 빠짐, `.prettierignore` 사고(실제로 한 번 났다), 저장소 밖에서는 `#preview-kit` 이 풀리지 않음(같은 파일 52~57).

**4. 공용 코드의 크기**
html-frame 은 약속 검사 486줄, 테스트 218줄, 틀 85줄이다. fragments 는 공용 976줄과 테스트 316줄, components 는 공용 904줄과 변환 243줄, 테스트 135~144줄이다(각 STATS 1~2절). 앞의 것은 검사기 하나이고, 뒤의 둘은 조립기나 빌드, 줄 찾기, 어긋남 비교까지 떠안는다.

**5. 확인 속도**
약속 검사는 html-frame 이 1605~3805ms, 나머지 둘이 500~600ms 다. 다만 부르는 방식이 달라서(MEASURED 121, 125, 127) 구조의 차이라고 단정할 수 없다. 테스트 시간은 비슷하다.

**6. 기존 검사와 온보딩에 닿는 곳**
세 구조 모두 `src/lib`, `scripts` 의 검증기를 0줄 고쳤다. html-frame 은 온보딩에 검사 한 줄만 더하고 `cp` 는 그대로다(README 267~269). 대신 검증기가 틀 CSS 를 보지 못해서, "서빙되는 한 장을 검증한다"는 ADR 0002 의 문장을 고쳐야 한다(STATS 69). fragments 와 components 는 온보딩에 조립이나 빌드 단계가 하나 생기고, 10단계가 원본 폴더 복사와 조립으로 바뀐다. 대신 ADR 0002 는 그대로 맞는다(fragments/STATS.md 39~41, 57. components/STATS.md 42~45).

## 무게별 순위

### 1. 새 항목 만들기가 단순한가
1위 html-frame. 파일 한 장에 빌드가 없고, 검사 두 번으로 끝났다(html-frame-s4b.md 64). 두 풀이 모두 한 번 실패했지만 둘 다 폴더가 없어서 생긴 일이고, 안내에 `mkdir` 한 줄이 빠진 탓이다(MEASURED 152). 문서를 고치면 사라진다.
2위는 components 와 fragments 사이에서 가리지 못함. components 는 두 풀이 모두 실패가 0이었다. 다만 타입 검사, 빌드, prettier 까지 단계가 여섯이고, 이스케이프 같은 새 지식이 든다. fragments 는 두 풀이 모두 "서빙 파일이 없다"는 지적을 한 번씩 받았다. 안내가 미리 말한, 구조에서 오는 한 단계다. 손으로 쓴 줄은 세 구조가 235~281줄로 비슷하다. 여섯 풀이 모두 안쪽의 꼴은 치지직을 베꼈다(MEASURED 153). 이것은 세 구조에 똑같이 남은 안내의 빈자리다.

### 2. 한꺼번에 고치기 쉬운가
1위는 fragments 와 components 사이에서 가리지 못함. 둘 다 태그 변경과 순서 변경에서 항목 원본을 하나도 고치지 않았다. 차이는 작고 양쪽으로 갈린다. fragments 는 줄 대응이 단단하지만, 어긋났을 때 메시지가 원본 줄로 옮겨지지 않는다. components 는 줄 찾기가 들여쓰기에 묶여 있다.
3위 html-frame. 틀 모양만 한 파일로 끝나고, 태그와 구역 순서는 29개 파일을 스크립트로 고쳐야 한다. 그 스크립트를 관리하는 곳도 없다. README 의 구역 표처럼 손으로 맞춰야 하는 사본도 하나 더 있다(MEASURED 66).

### 3. 지금 있는 검사와 온보딩 흐름을 얼마나 살리나
1위 html-frame. 저자가 쓰는 파일과 복사가 그대로이고, 검사 한 줄만 더해진다. 다만 검증기가 틀 CSS 를 보지 못하는 빈틈을 떠안는다.
2위 fragments. 조립 단계가 하나 더해지고, md 가 끝난 뒤에야 조립할 수 있다. 검증기는 완결된 서빙 파일을 본다.
3위 components. 빌드, 포맷, 타입 검사가 흐름에 들어오고, 스테이징 중에는 줄 찾기를 쓸 수 없다(README 193). 저자 프롬프트는 HTML 대신 TS 모듈을 가르쳐야 한다.

## 측정이 말해 주지 않는 것
- 29개 항목으로 옮길 때의 일. 변환 스크립트는 두 항목에서만 손 없이 돌았다. 나머지 27개의 꼴에서도 되는지는 묶음에 없음.
- 공용 코드를 고치는 PR 과 항목 PR 이 함께 열릴 때, 다시 만든 서빙 파일끼리 충돌하는 빈도와 그 처리 비용. 묶음에 없음.
- html-frame 의 약속 검사가 CI 에서 모든 항목을 도는지, 아니면 두 항목에 묶여 있는지. 묶음에 없음.
- 틀을 바꿨을 때 대비 기준선이 모든 항목에서 한꺼번에 움직이는 것을 다루는 비용. 어느 가지도 `pnpm gates` 와 브라우저 확인을 돌리지 않았다(MEASURED 100~101).
- 몇 해 뒤 저자 프롬프트와 리뷰어 프롬프트를 고치는 비용. 세 구조 모두 프롬프트를 고치지 않았다.
- 작은 어긋남 하나: components 의 테스트 줄 수가 135(STATS 16)와 144(STATS 36)로 두 번 다르게 적혀 있다.

## 커스텀 태그
- 기존 검사 셋이 아무것도 막지 않았다. 하지만 그 "통과"는 검증기가 속성 안의 이름표와 다크 이름표를 보지 못한 채 낸 통과다. 속성에 심은 금지 문구도 그대로 통과했다(custom-tags/README.md 83, 109).
- 스크립트를 끄면 구역 제목과 칸 이름표 20개가 사라지고 틀 스타일이 하나도 걸리지 않는다. `iframe.js` 가 "스크립트 없이 열면 라이트 테마다"라고 한 약속이 깨진다(같은 파일 133~139).
- 그리는 코드가 모든 프리뷰가 싣는 `iframe.js` 에 109줄 더해졌다. 그래서 유지보수할 곳이 공용 런타임으로 옮겨 간다(custom-tags/STATS.md 14).
