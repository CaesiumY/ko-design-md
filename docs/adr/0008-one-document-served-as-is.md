# 항목의 DESIGN.md 를 변환 없이 그대로 표준 문서로 발행한다

ADR 0003 은 토큰을 frontmatter 로 옮겨 항목 파일 자체를 명세 문서로 만들면서도, 표준 도구용 DESIGN.md 를 어댑터가 요청마다 계산하는 두 번째 표현으로 남겼다. 어댑터가 필요했던 이유는 항목 파일이 표준 린트를 어댑터 없이는 통과하지 못한다는 것이었다. 그런데 토큰이 frontmatter 로 간 뒤에는 항목 파일을 그대로 린트한 결과가 어댑터 출력과 같았다. 해석되는 토큰도, 에러 18건도 같았고, 차이는 경고 3건뿐이었다. 그 3건은 본문 yaml 펜스에서 나왔다. 공식 린터는 본문 yaml 펜스를 frontmatter 와 같은 스키마 네임스페이스로 병합하는데, 이 점 말고는 두 표현이 서로에게 보태는 것이 없었다. 그래서 그림자는 frontmatter `elevation:` 으로 옮기고 나머지 본문 yaml 펜스는 `text` 로 바꾼다. 그다음 어댑터를 걷어내고 항목의 DESIGN.md 하나만 발행한다. `/services/{slug}/DESIGN.md` 는 `/services/{slug}/llms.txt` 와 같은 바이트를 명세의 파일명으로 내보내는 주소가 된다.

## Considered Options

- **어댑터를 유지한다.** 항목 파일과 같은 결과를 내는 변환 계층을 계속 떠안게 된다. 게다가 항목 파일이 표준에서 멀어져도 어댑터가 그 차이를 가려서, 파일을 직접 가져간 소비자만 어긋난 문서를 받는다. ADR 0003 이 막으려던 바로 그 경우다.
- **표준 스키마에 없는 키를 항목 파일에서 뺀다.** slug·logo·날짜 같은 카탈로그 메타와 `fonts`·`gradients` 같은 보조 맵이 대상이다. 그러나 린터는 이 키들을 문제 삼지 않고, 빼려면 메타를 둘 다른 파일이 새로 필요하다.
- **본문 yaml 펜스를 토큰 섹션에서만 막는다.** 그러면 그림자·모션·컴포넌트 스펙 펜스가 다시 들어올 수 있다. 그런 펜스가 하나라도 생기면 발행되는 문서가 린트에서 달라진다. 실제로 `wanted` 는 컴포넌트 펜스끼리 키가 겹쳐 문서 전체가 0토큰이 된 적이 있다.

## Consequences

- 본문 yaml 펜스는 어느 섹션에 있든 검증기가 막는다(`body-yaml-fence`). 네 토큰 섹션 안에서는 종전의 `token-fence` 가 막는다. 그림자는 frontmatter `elevation:` 에 두고, 모션과 컴포넌트 스펙은 본문 `text` 펜스에 둔다. `text` 펜스의 값은 독자에게는 보이지만 린터는 읽지 않는다.
- 그림자는 사이드카가 frontmatter `elevation:` 에서만 읽는다. 이관 직후 사이드카는 바이트 단위로 이관 전과 같았다.
- 코퍼스 테스트와 `validate:spec` 은 항목 파일을 그대로 린트한다. 본문 펜스가 스키마로 읽힐 때 나오는 `unknown-key`·`token-like-ignored` 는 0건으로 고정한다. `test:http` 는 두 주소가 같은 본문을 내는지 확인한다.
- 어댑터가 태그라인에서 만들던 명세의 `description` 은 발행하지 않는다.
- 항목 메타(slug·logo·날짜)와 카탈로그 고유 맵이 표준 도구 쪽에도 그대로 실린다.
