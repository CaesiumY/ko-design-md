# 항목의 DESIGN.md 를 변환 없이 그대로 표준 문서로 발행한다

ADR 0003 은 토큰을 frontmatter 로 옮겨 항목 파일 자체를 명세 문서로 만들었다. 그러면서도 인용과 프로비넌스를 지키는 항목 파일과 별도로, 표준 도구용 DESIGN.md 를 어댑터가 요청마다 계산하는 두 번째 표현으로 남겼다. 그 두 번째 표현이 할 일은 항목 파일이 표준 린트에서 걸리는 부분을 걸러 내는 것이었는데, 토큰이 frontmatter 로 간 뒤에는 그 부분이 거의 남지 않았다. 항목 파일을 그대로 린트한 결과가 어댑터 출력과 같았다. 해석되는 토큰도, 에러 18건도 같았고, 차이는 경고 3건뿐이었다. 그 3건은 본문 yaml 펜스에서 나왔다. 공식 린터는 본문 yaml 펜스를 frontmatter 와 같은 스키마 네임스페이스로 병합한다. 어댑터가 따로 보태는 것은 태그라인에서 만든 `description` 하나였다.

그래서 그림자는 frontmatter `elevation:` 으로 옮기고, 나머지 본문 yaml 펜스는 `text` 로 바꾸고, 어댑터를 걷어낸다. 인용과 프로비넌스는 항목 파일에 그대로 있으므로 ADR 0003 이 두 번째 표현을 두어 지키려던 것은 잃지 않는다. `/services/{slug}/DESIGN.md` 는 `/services/{slug}/llms.txt` 와 같은 바이트를 명세의 파일명으로 내는 주소가 된다.

## Considered Options

- **어댑터를 유지한다.** 항목 파일과 같은 결과를 내는 변환 계층을 계속 떠안는다. 더 나쁜 점은 항목 파일이 표준에서 멀어져도 어댑터가 그 차이를 가린다는 것이다. 그러면 파일을 직접 가져간 소비자만 어긋난 문서를 받는다. ADR 0003 이 막으려던 바로 그 경우다.
- **표준 스키마에 없는 키를 항목 파일에서 뺀다.** slug·logo·날짜 같은 카탈로그 메타와 `fonts`·`gradients` 같은 보조 맵이 대상이다. 그러나 린터는 이 키들을 문제 삼지 않고, 빼려면 메타를 둘 다른 파일이 새로 필요하다.
- **본문 yaml 펜스를 토큰 섹션에서만 막는다.** 그러면 그림자·모션·컴포넌트 스펙 펜스가 다시 들어올 수 있다. 그런 펜스가 하나라도 생기면 발행되는 문서가 린트에서 달라진다. 실제로 `wanted` 는 컴포넌트 펜스끼리 키가 겹쳐 문서 전체가 0토큰이 된 적이 있다.

## Consequences

- "본문에 yaml 펜스가 없다"가 발행의 전제가 된다. 이를 지키는 게이트와 저작 규칙은 `CLAUDE.md` 에 있다.
- 그림자의 출처가 본문 펜스에서 frontmatter 로 바뀌었다. 이관 직후 사이드카는 바이트 단위로 이관 전과 같았으므로, 사이트 Tokens 탭과 `use-design-md` 가 보는 값은 바뀌지 않았다.
- 명세의 `description` 은 발행하지 않는다.
- 항목 메타(slug·logo·날짜)와 카탈로그 고유 맵이 표준 도구 쪽에도 그대로 실린다.
