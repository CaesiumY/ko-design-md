### 라이트 누출 — 다크 시트에 대응 선언이 아예 없는 경우

`vapor-ui` 의 `.wordmark { color }` 는 원본 dark.html 에 **없다.** 병합본은
라이트 시트의 선언을 물려받아 다르게 그린다. 중화할 선택자가 다크 쪽에 없으므로
**어떤 명시도 값으로도 못 고친다.**

해법은 중화 규칙을 emit 하는 것이 아니라 — CSS 에는 "선언 취소" 값이 없고
`revert`/`unset`/`initial` 은 그 자체가 선언이라 여전히 적용돼야 할 다른 규칙까지
누른다 — **라이트 전용 선언을 라이트 스코프로 옮기는 것**이다.

```
  .wordmark { font-size: 18px; …; -webkit-text-fill-color: transparent }
:where(html[data-theme="light"]) .wordmark { color: var(--vp-fg-secondary-200) }
```

- 이동 단위는 **선언**이지 규칙이 아니다. `.wordmark` 의 나머지 선언은 공유로 남는다.
- 가드는 `:where()` 로 감싸 명시도 0. 맨 접두를 쓰면 명시도가 올라가 아래
  seed-design 과 같은 버그를 라이트 쪽에 복제한다.
- 속성은 shorthand/longhand 패밀리로 묶어 판정한다. 라이트 `border-top` 의 짝이
  다크 `border-top-color` 뿐일 때 부재로 보면 다크에서 width·style 이 증발한다.

실측: 라이트 전용 선언 192개 / 12 사이트 / 8 슬러그. 적용 시 다크 13행 → 4행
(vapor-ui 7→0, krds 2→0), 라이트 0 유지, `validate:previews`·`audit:oklch` 출력
바이트 동일, brotli 최대 +293 B.

**처방 (착지): `scopeLightOnly` in `scripts/merge-preview-themes.mjs`.** 위 설계
그대로 — 선언 단위 이동, `:where()` 가드, shorthand/longhand 패밀리 판정. 결과는
예측대로 다크 13 → 4 · 라이트 0 유지였다.

**다만 192개가 아니라 29개면 된다.** 위 실측이 큰 이유는 **두 반쪽이 같은 요소를
다른 이름으로 부르기 때문**이다 — 라이트는 `:root { --brand-orange }`, 다크는
`[data-theme="dark"] { --brand-orange }` 로 쓴다. 문자열로 비교하면 그런 토큰이
전부 "라이트 전용" 으로 읽혀 11st 혼자 58개가 옮겨졌다(패리티는 어느 쪽이든
성립한다 — 다크 자기 블록이 어차피 이겼다). 그래서 부재 판정 키는 루트 컴파운드
(`:root` · `html` · `[data-theme=…]` 의 조합)를 하나로 접고, 자손 앞에 붙은 루트
컴파운드도 벗긴다(`[data-theme="dark"] .hero` ≡ `.hero`, 그 문서 안에서는 같다).
**29개 / 7 슬러그로 줄었고 결과는 동일하다** — 라이트 0, 다크 13 → 4. 옮기는 선언이
적을수록 diff 가 읽히므로 이쪽을 채택했다.

**가드 표기를 `:not([data-theme="dark"])` 로 쓰면 안 된다.** `findPreviewDrift`
(`src/lib/oklch-drift.ts`) 는 선택자에 `[data-theme="dark"` 문자열이 나타나기만
하면 그 블록을 다크로 보고 건너뛴다. 그 표기를 쓰면 **라이트 토큰 블록이 통째로
감사에서 사라진다** — 11st 33개 → 0개, vapor-ui 43개 → 0개. 게이트는 여전히
exit 0 이라 조용히 실명한다. `[data-theme="light"]` 로 쓰면 HEAD 와 동일하게
동작한다.

### baemin — `<template>` 이 인접 형제 결합자를 끊는다

`.section + .section { border-top: 1px solid var(--bm-border-1) }` 는 두 시트에
글자 그대로 동일하다. 문제는 **`<template>` 이 엘리먼트**라는 것이다. 런타임의
`insert` 는 다크 노드를 앵커 `<template>` **앞에** 넣으므로 다크에서 순서가
`[다크 section][template][section]` 이 되고 `+` 가 불발한다. 그래서
`border-top-color` 가 `currentColor` 로 떨어진다.

라이트가 멀쩡한 것은 그 자리의 앞 형제가 원래 `.section` 이 아니었던 **우연**이다.
**즉 이건 baemin 하나의 문제가 아니라 병합 메커니즘 자체의 함정이고, 형제
결합자를 쓰는 모든 프리뷰에 잠복한다.**

고칠 자리는 CSS 가 아니라 런타임·생성 단계다. `collect()` 가 `<template>` 을
주석 노드 마커로 교체하면 형제 사슬에 안 걸린다. 다만 스크립트 없이 여는 라이트
경로에는 template 이 그대로 남으므로, 생성 단계에서 앵커를 형제 사슬 밖으로
빼는 것까지 함께 봐야 한다.

**처방 (착지): `collect()` 가 `<template>` 을 `document.createComment()` 로
교체한다.** 내용은 그 전에 `importNode` 로 떠 둔다. 주석은 엘리먼트가 아니므로
`+`/`~` 를 안 끊고 `:nth-child` 도 안 밀며, template 을 고른 이유였던 불활성
성질(렌더·접근성 트리·find-in-page·복사 어디에도 안 걸림)을 그대로 갖는다.
baemin 다크 3행 → 0. 라이트→다크→라이트→다크 순환도 17/17 멱등이다(단일 전환
DOM 과 바이트 동일).

**생성 단계는 손대지 않았다 — 재보고 내린 판단이다.** 파일 포맷의 `<template>` 은
생성물이기만 한 게 아니라 **손으로 쓰는 규약**이고
(`.claude/agents/preview-html-author.md`), `src/lib/preview-halves.ts` 가 두 반쪽을
되짚는 근거이며, 검증기의 요소 워크가 그 안을 들여다본다. 다크 마크업을 주석
데이터로 옮기면 작성자가 `-->` 를 피해 가며 마크업을 손으로 이스케이프해야 하고
검증기 시야에서 사라진다. **그리고 그 경로가 실제로 깨지는지 재 봤다** —
런타임을 통째로 막고(= template 이 흐름에 남는 유일한 경우) 재면 17개 슬러그
전부 원본 light.html 과 계산 스타일까지 일치한다. **잠복이지 발현이 아니다.**
`_runtime/iframe.js` 의 주석이 이 판단과 실측을 갖는다.

### seed-design — 스코프가 명시도를 올려 tokens.css 를 이긴다

`.sd-tag { font-weight: 500 }` 은 라이트·다크 양쪽에 똑같이 있다. 스코프가
`[data-theme="dark"] .sd-tag` (0,2,0) 으로 만들면서 `tokens.css` 의
`.catalog-disclaimer b` (0,1,1) 를 이겨버린다. 원본 dark.html 에서는 tokens.css 가
정당하게 이겨 600 이었다.

라이트 쪽 처치로는 닿지 않는다. 다크 스코프의 명시도를 원본 관계가 보존되도록
조정해야 하는데, 아래 기각 목록이 보여주듯 전역 조정은 전부 다른 슬러그를 깬다.

**처방 (착지): `selectorsOutrankedByTokens` — 국소 평탄화.** 접두가 (0,1,0) 을
더하는 것이 페이지 안에서는 무해하다(라이트 쌍둥이도 같은 무게라 순서만 있으면
된다). **문제는 `tokens.css` 가 어느 반쪽에도 속하지 않아 그 가산을 안 받는
제3의 시트라는 것**뿐이다. 그래서 **접두가 tokens.css 규칙을 타 넘는 선택자에만**
`:where([data-theme="dark"])` 를 쓰고 나머지는 전부 full weight 로 둔다.

판정 조건은 "엄격히 사이" 하나다 — `명시도(tokens) > 명시도(선택자)` 이고
`명시도(선택자+접두) > 명시도(tokens)`. 동률인 tokens 규칙은 이미 순서로 지고
있고(링크가 페이지 `<style>` 보다 앞) 접두 후에도 계속 지므로 뒤집힘이 없다.

**"같은 요소를 가리키는가" 는 패턴이 아니라 문서로 판정한다.** `.sd-tag` 와
`.catalog-disclaimer b` 는 글자를 하나도 공유하지 않고, 같은 `<b>` 를 맞출 뿐이다.
jsdom 이 이미 다크 반쪽을 들고 있으므로 두 선택자가 맞추는 요소 집합을 실제로
구해 교집합을 본다. **전 카탈로그에서 걸린 선택자는 `.sd-tag` 하나** (seed-design,
+8 B). seed-design 다크 1행 → 0.

## 기각한 접근 — 실측치와 함께

넷 다 돌려보기 전에는 옳아 보인다. 그래서 숫자를 남긴다.

| 방식 | 결과 |
| --- | --- |
| 단일 `[data-theme="dark"]` | 라이트 0 · 다크 13행 ← 현재 채택 |
| 속성 3회 반복 `[dt][dt][dt]` | 11st 10 → **373** (증가폭 불균일: `:root` +2, `.x` +3) |
| 캐스케이드 레이어 `@layer` | 라이트 0 → **348** (`tokens.css` 가 비레이어라 위로 올라섬) |
| `:where([data-theme="dark"])` | baemin 1 → **340** (동률에서 순서가 뒤집힘) |

레이어가 실패하는 이유가 특히 반직관적이다 — **레이어에 속하지 않은 선언은
레이어에 속한 선언을 이긴다.** 페이지 CSS 를 레이어로 감싸는 순간 공유
`tokens.css` 가 그 위로 올라선다.

그 관찰이 국소 처치의 근거가 됐다 — 세 방식이 건드리려던 것은 사실 **"페이지 CSS
대 페이지 CSS"가 아니라 "페이지 CSS 대 비스코프 제3 시트"** 관계 하나뿐인데,
셋 다 페이지 내부 관계까지 같이 흔들었다. 표의 마지막 줄(전역 `:where()`)이
seed-design 을 고치면서 baemin 을 340행으로 만든 것이 그 대가다. 조건을 "제3
시트를 타 넘는 선택자" 로 좁히면 전 카탈로그에서 한 줄만 남는다.

**즉 이 표는 여전히 유효하다** — 기각된 것은 전역 적용이고, 채택된 것은 같은
도구의 국소 적용이다. 전역으로 되돌리려는 다음 사람은 위 숫자를 먼저 볼 것.

## 남은 부채

**생성 단계의 `<template>` 은 그대로다.** 런타임이 도는 경로(사이트 iframe, 즉
실제로 서빙되는 형태)에서는 주석으로 교체되므로 형제 사슬에 안 걸리지만,
**스크립트 없이 여는 라이트 경로에는 남는다.** 지금은 17개 전부 원본과 일치하니
발현된 결함이 아니라 잠복이고, 포맷을 바꾸는 비용(손 작성 규약 ·
`preview-halves.ts` · 검증기 시야 · `-->` 이스케이프)이 그보다 크다고 판단했다.
되짚는다면 근거는 「baemin」 절의 처방 항에 있다.

**이 잠복을 깨울 수 있는 것은 새 프리뷰다** — 손으로 쓴 `<template>` 이 `+`/`~`
사슬이나 `:nth-child` 를 가로지르는 자리에 놓이면 스크립트 없는 라이트에서만
어긋난다. 기계 검사는 없다.

## 착지 뒤에 남아 있던 결함 (2026-08-16, 2차)

위 처방으로 **17개 슬러그의 수치는 0** 이 됐지만, 0 을 만든 이유가 우연인 자리가
넷 있었다. 전부 새 프리뷰 하나면 발현한다.

| 자리 | 왜 17개는 무사했나 | 처방 |
| --- | --- | --- |
| `insert` 앵커가 `swap` 앵커와 겹침 | `insert` op 3건이 전부 `swap` 을 안 쓰는 앵커에 붙었다 | 생성기가 이미 붙은 variant 템플릿 **뒤에** 삽입 |
| 들여쓴 `<template>` | 생성기는 붙여 쓴다 — 손 작성에서만 난다 | 런타임·`preview-halves` 가 공백·주석을 건너뛰고 **자식 전부**를 옮김 |
| 문 형태 at-rule 이 다음 prelude 를 삼킴 | gmarket 의 첫 다크 규칙이 마침 `[data-theme="dark"] {` 였다 | prelude 를 depth 0 의 마지막 `;` 에서 자름 |
| `identical-style-blocks` | — (전 슬러그 확정 오미였다) | 접두 벗기기 + 비교를 정규형에서 (아래 3차 절) |

**앵커 겹침이 왜 "읽는 쪽 방어" 로 안 풀리는지**가 이 라운드의 교훈이다.
`[l1][insert][swap]` 순서에서 `swap` 이 무엇을 바꿔야 하는지는 **파일에 안 적혀
있다** — `swap` 은 앞 노드로 정의되는데 그 자리에 insert 템플릿이 서 있다.
읽는 쪽이 주석 앵커를 건너뛰어 `l1` 을 찾아내도 **출력 순서가 원본과 뒤집힌다**
(dark 는 `d1` 다음 `X` 인데 `X` 다음 `d1` 이 된다). 그래서 고칠 자리는 쓰는 쪽
하나뿐이고, 읽는 쪽은 그 형태를 **거부**한다(`assertReadableVariants`).

> **이 문단은 틀렸다 — 아래 3차 절이 반증한다.** 그대로 두는 이유는 그럴듯해
> 보이는 전제가 어디서 왔는지 남기기 위해서다.

`identical-style-blocks` 를 되살릴 때 **다크 시트를 재직렬화하면 안 된다.**
`선택자 + " {" + 본문 + "}"` 로 다시 쓰면 라이트의 `:root{…}` 와 다크의
`:root {…}` 가 공백 하나로 갈려, 룰이 "항상 발화" 대신 "여전히 발화 불가" 가 된다
(검증기의 `normalizeStyle` 은 `\s+`→` ` 만 한다). 접두 문자열만 잘라내고 나머지
바이트는 건드리지 않는다.

실측 (27개 속성 · 폭 1440/976/768/375 · 17/17): 라이트 0 · 다크 0, 테마 순환 멱등,
런타임 차단 라이트도 원본 일치, **렌더된 innerText 도 34 반쪽 전부 일치**,
`validate:previews`·`audit:oklch` 출력은 HEAD 와 바이트 동일, 변환기 재실행 →
설치본과 17/17 바이트 동일(gmarket 만 `@import` 처방으로 10 B 줄어 갱신).

> **이 마지막 두 수치가 4차에서 뒤집혔다.** "HEAD 와 바이트 동일" 은 기준선이
> HEAD 라서 *줄어든 시야가 그대로 고정된 것*을 통과로 읽었고(다크 주석 696개
> 소실), "17/17" 은 실제로 **16/17** 이었다 — 손으로 고친 baemin dark.html 이
> 입력에 있었기 때문이다. 아래 4차 절.

## `identical-style-blocks` 는 2차에도 죽어 있었다 (2026-08-16, 3차)

**바로 위 문단이 틀렸다.** "재직렬화하면 안 된다" 는 처방은 옳지만, 그 처방을
따를 대상이 남아 있지 않다 — **재직렬화는 이미 변환기가 했다.** `scopeBlock`
(`scripts/merge-preview-themes.mjs`) 은 다크 시트를 다시 쓴다: 언제나
`prelude + " {"`, 선택자 목록은 `", "` 로, 규칙은 개행으로 다시 잇는다.
`unscopeDarkSheet` 가 접두만 벗겨도 **라이트가 들고 있는 저자의 바이트와는 여전히
다르다.** 즉 2차의 ~110줄은 게이트에서 관측되는 것이 하나도 없었다.

실측(다크 반쪽이 라이트의 바이트 단위 복사인 슬러그): 정규화 후 라이트 36,303자
대 다크 36,632자, 첫 분기 오프셋 4324 에서 `.ic{`(라이트) 대 `.ic {`(다크).
`{`·`}`·`,` 주변 공백만 지우면 두 문자열이 **완전히 같아진다** — 잔차는 100%
변환기 공백이고 내용 차이는 0 이다. 분할 배치에서는 발화, 병합 배치에서는 무음.

**처방: 바이트 복원을 포기하고 정규형에서 비교한다.** 바이트는
`preview-halves.ts` 가 파일을 받기 전에 이미 없어졌으므로 복원할 대상이 아니다.
`preview-validator.ts` 의 `normalizeStyle` 이 양쪽 모두에서 `{};,` 주변 공백을
지운다. 접두 벗기기는 그대로 필요하다 — 둘은 한 쌍이다.

**두 번째 누출: 루트 스코프의 두 표기.** `scopeSelector` 는 앞선 `:root` 를
속성으로 **치환**하고 저자가 직접 쓴 `[data-theme="dark"]` 는 그대로 두므로,
병합된 파일에는 어느 쪽이었는지가 남지 않는다. `codeit` 이 그 슬러그다 — 두 반쪽이
`:root` 블록과 `[data-theme="dark"]` 블록을 함께 담은 같은 이중 테마 시트를 싣는다.
**분할 배치에서는 이 룰이 발화했고 병합 배치에서는 사라졌다.** 정규형에서 두 표기를
접으면 돌아온다. 전 카탈로그에서 판정이 바뀌는 슬러그는 codeit 하나이고, 나머지
16 은 그대로다.

그래서 **이번 라운드는 게이트 출력을 바꾼다** — codeit 이 `1 warn` 에서 `2 warn`
으로, 합계가 43 → 44 로 는다. 위 절들의 "HEAD 와 바이트 동일" 은 *감사 시야가
줄지 않았다*는 증거였는데, 여기서는 **줄었던 시야가 origin/main 수준으로 돌아온
것**이라 방향이 반대다. block 은 여전히 0, exit 0.

**테스트가 왜 이걸 못 잡았나.** `preview-halves.test.ts` 의 복사 질문 테스트는
병합 파일을 **손으로 만든다.** 그 손 작성 공백이 마침 변환기의 정규형과 같았고
중첩 at-rule 도 없어서, 재직렬화 자체를 볼 수가 없었다. 그래서 3차의 테스트는
`preview-merge-anchors.test.ts` 에서 **진짜 변환기를 돌린 뒤** 실제
`validatePreviewPair` 에 물어본다(`.ic{` · 들여쓴 `@media` · `.a,.b`). 처방을
빼면 그 둘이 실패하는 것까지 확인했다.

**같이 고친 비대칭 둘** (같은 함수, 오늘은 도달 불가지만 조용히 틀린다):
`unscopeSelector` 가 `[data-theme="dark"].panel` 을 `:root.panel` 로 되돌리지
않아 변환기의 역이 아니었고(카탈로그 반쪽에 `:root` 컴파운드는 0건),
`statementCut`/`unscopeDarkSheet` 가 주석을 건너뛰지 않아 주석 속 `{` 하나가
**그 뒤 규칙 전부를 스코프된 채로 남겼다.** 주석은 이제 오프셋 보존 방식으로
공백화해 스캔하고, 내보내는 바이트는 원본에서 자른다.

3차 실측: 라이트 0 · 다크 0 (27개 속성 · 폭 1440/976/768/375 · 17/17, 원본 반쪽
대조 · 모션 차단 후 측정), 렌더된 innerText 34/34 일치, DOM 잔존 `<template>` 0,
`npx tsc --noEmit` 0 · `npx vitest run` 582 passed / 45 files ·
`validate-preview.ts` exit 0 · `audit-oklch.ts` exit 0 · 0 mismatched.
**서빙되는 바이트는 한 글자도 안 바뀌었다** — 이번 라운드가 손댄 것은
`src/lib/preview-{halves,validator}.ts` 와 그 테스트뿐이라 `public/` diff 가
2차와 동일하다(불변식 1·2 가 영향받을 경로가 없다는 뜻).

## 스캔이 한 겹 모자랐다 · 변환기가 자기 출력을 못 냈다 (2026-08-17, 4차)

3차가 고친 것은 **주석 속 `{`** 였다. 같은 함수의 같은 워크가 **문자열 속 `{`** 도
똑같이 놓치고 있었고, 바로 옆 `statementCut` 이 이미 따옴표를 추적하고 있어서
비대칭이 한 파일 안에 드러나 있었다. 3차가 주석을 고친 이유(생성기는 못 만들지만
preview.html 은 손 작성 규약이다)가 문자열에는 더 강하게 적용된다 —
`content: "{"` 는 코드·CSS 문법을 보여주는 프리뷰에서 평범하다.

실측(수정 전): `.x::after { content: "{" }` 뒤의 두 규칙이 `[data-theme="dark"]`
접두를 단 채로 나왔다. `content: "}"` 는 한 규칙 뒤부터, `content: "x"` 는 셋 다
깨끗했다. 그 상태가 곧 `identical-style-blocks` 가 다시 침묵하는 상태다.

**처방: `blankInert` — 주석과 문자열을 오프셋 보존 방식으로 함께 공백화한다.**
`src/lib/preview-halves.ts` 와 `scripts/merge-preview-themes.mjs` 양쪽에 같은
모양으로 둔다(전자는 게이트가 import 하는 타입 소스, 후자는 단독 `.mjs` 스크립트라
서로 빌드 의존을 걸 수 없다).

**단 문자열 공백화는 경계에는 옳고 텍스트에는 틀리다.** 이걸 놓쳐서 한 번
잘못 갔다 — `[data-theme="dark"]` 가 `[data-theme=        ]` 로 뭉개지면
`ROOT_COMPOUND` 가 그걸 못 알아보고, 다크 토큰 블록이 `:root` 로 키잉되지 않아
**라이트 토큰 전부가 "라이트 전용" 으로 읽힌다**(11st 0 → 58, vapor-ui 3 → 95 선언이
라이트 가드 뒤로 이동). 그래서 `eachRule` 은 뷰를 둘 받는다 — **경계는 주석+문자열
공백화본에서, 선택자 텍스트는 주석만 공백화한 본에서.** 고친 뒤 라이트 시트는
17/17 설치본과 바이트 동일이다.

### 병합이 다크 시트의 주석 696개(36,417 B)를 지우고 있었다

`scopeDark` 가 `stripComments` 를 먼저 돌렸다. 라이트 시트는 오프셋 편집이라
주석이 보존되므로 **비대칭**이었고, 결과는 두 가지다.

- **내용 소실.** wanted 다크 시트의 `/* #171719 */` 류 6건과 bezier 1건은 라이트
  반쪽에 대응이 없다. 이 PR 이 `dark.html` 을 지우므로 저장소 어디에도 남지 않게
  된다.
- **시야 축소.** `origin/main` 의 분할 반쪽 판정과 병합 판정을 전 슬러그·전 룰로
  대조하면 `hex-colors-present` 가 4건 적었다 — codeit 2→1, line-design-system
  2→1, yeogi 2→1, wanted 1→0.

**처방: `stripComments` 를 없애고 `scopeBlock` 이 스캔/바이트를 분리한다.** 본문
안 주석(274개)은 본문이 통째로 복사되므로 따라오고, prelude 주석(422개)은 그
규칙 앞에 그대로 내보낸다. 선택자 앞 주석을 선택자의 일부로 읽지 않도록 lead 영역은
스캔에서 잰다(안 그러면 `/* note */ :root` 가 자손 `:root` 가 되어 아무것도 안 맞는다).

**대조 결과: 병합 판정이 `origin/main` 분할 판정과 전 슬러그·전 룰 일치(48 = 48).**
주석 총량도 696개 / 36,417 B 로 원본과 같다.

**이 결함이 6라운드를 통과한 이유**는 매번 "병합본 vs HEAD" 만 쟀기 때문이다.
`origin/main` **분할 판정**을 기준선으로 삼는 대조는 이번이 처음이고, 그 대조가
없으면 "바이트 동일" 은 *시야가 줄지 않았다* 가 아니라 *줄어든 채로 고정됐다* 를
뜻할 수 있다.

### 변환기가 shipped `baemin/preview.html` 을 재현하지 못했다 (16/17)

설치본에 있는 `section-dark-gap` 클래스는 **어느 커밋의 반쪽에도 없다.** 즉 손으로
고친 dark.html 로 생성된 파일이었고, 그 편집은 위 「측정 방법」 절에 *하네스 보정*
으로만 적혀 있었지 **생성 전제라고 말하는 곳이 없었다.** 규칙이 하나도 안 걸리는
불활성 마커라 렌더는 정상이었지만, 재실행하면 3,472줄(설치본 3,036)에 variants 5(7)
짜리 다른 병합이 나왔다 — LCS 가 공유 Components `<section>` 과 다크 전용 면책
`<section>` 을 짝지어 `<section>` 하나를 통째로 swap 템플릿에 복제한 것이다.

두 후보는 `sig`(태그+클래스)가 같아 **길이가 같은 최적 정렬이 둘** 생긴다. 그래서
길이를 가르는 게 아니라 **동률을 가르는** 2차 점수를 넣었다.

- `deepSig` = 자식·손자의 태그+클래스. baemin 은 `DIV|container(DIV|gap-card)` 대
  `DIV|container(DIV|section-head,DIV|showcase)` 로 갈린다.
- dp 를 `matches * 4096 + deepSig일치수` 로 두어 **2차 점수가 1차 매치를 절대 못
  산다**(두 리스트 길이는 250,000 셀 상한 때문에 짧은 쪽이 500 이하).
- **매치를 막지 않는다**는 점이 기각된 "내용 유사도 타이브레이크" 와 갈리는
  지점이다. 그건 매치 자체를 막아서 baemin 을 고치고 kyobobook·line-design-system
  을 깼다(임계 0.05~0.25 전부).
- `sig()` 독스트링이 `childElementCount` 를 키에 넣는다고 적고 있었으나 **구현에
  없었고, 넣어도 baemin 은 안 고쳐진다**(두 후보 다 자식 1개 — 재실행해 바이트
  동일 확인). 독스트링을 실제 동작으로 고쳤다.

**결과: 편집 없는 `origin/main` 두 반쪽에서 변환기 재실행 → 설치본과 17/17 바이트
동일.** baemin 설치본에서는 유령 클래스가 사라진다(마크업 diff 는 그 한 줄뿐).

### 4차 실측

## 스캔이 괄호를 세지 않았다 (2026-08-17, 5차)

3차는 **주석 속** 구분자를, 4차는 **문자열 속** 구분자를 고쳤다. 남은 것은
**괄호 속 콤마**였고, 이번에도 바로 옆 `statementCut` 이 이미 paren 뎁스를 세고
있어 같은 비대칭이 한 파일 안에 드러나 있었다. 콤마 스캔 세 곳
(`scopeSelectorList` · `splitSelectors` · `splitOnScan`) 은 스캔이 보는 **모든**
콤마에서 잘랐다.

**실측(수정 전).** 픽스처 슬러그를 만들어 변환기를 돌린 출력:

```
[data-theme="dark"] :is(.a, [data-theme="dark"] .b) .x { color: white }
[data-theme="dark"] .card:not(.muted, [data-theme="dark"] .ghost) { color: black }
[data-theme="dark"] .grid:has(> .item, [data-theme="dark"] > .row) { gap: 8px }
```

라이트 시트도 같이 깨진다 — `color` 만 라이트 전용이면
`:where(html[data-theme="light"]) :is(.a, :where(html[data-theme="light"]) .b) .x`
가 나온다.

의미가 바뀐다. `:is()`/`:not()` 는 인자 중 **최대** 명시도를 취하므로 접두가
안으로 들어가면 (0,1,1) → (0,2,1) 로 올라가 캐스케이드가 뒤집힐 수 있다 —
`selectorsOutrankedByTokens` 가 국소 처치까지 해 가며 막던 바로 그 부류다.
`:has()` 는 명시도가 아니라 **뜻**이 달라진다: `:has(> .item, [dt] > .row)` 의
둘째 팔은 "어트리뷰트를 단 자손의 자식 .row" 를 찾는데, 그 어트리뷰트는 `<html>`
에 있어 누구의 자손도 아니다 — **영영 안 맞는다.**

**처방: `splitTopLevel`.** `blankInert` 가 만든 오프셋 보존 스캔 위에
`statementCut` 과 같은 모양의 paren 카운터를 얹어, 콤마가 괄호 밖일 때만 자른다.
`scripts/merge-preview-themes.mjs` 와 `src/lib/preview-halves.ts` 양쪽에 같은
모양으로 둔다(4차의 `blankInert` 와 같은 이유로 공유 모듈이 아니다).

**읽는 쪽 피해는 쓰는 쪽보다 좁다 — 재 보고 확인했다.** `unscopeSelector` 는
접두를 벗기기만 해서 접두 없는 팔에는 무동작이고 조각은 잘린 콤마로 다시 이어지므로,
분할이 살아 있는 채로도 `:is(.a, .b) .x` · `.card:not(.muted, .ghost)` ·
`.grid:has(> .item, > .row)` · 진짜 선택자 목록이 **전부 바이트 그대로** 돌아왔다.
어긋난 것은 **팔 자체가 스코프 컴파운드인 경우** 하나다 —
`:is(.x, [data-theme="dark"].y)` 가 잘려 둘째 팔이 `unscopeSelector` 의 컴파운드
분기를 타고 `:is(.x, :root.y)` 로 나왔다. 저자가 쓰지 않은 선택자가 모든 pair 룰에
그대로 전달된다. 회귀 테스트는 **실제로 달라지는 그 모양으로** 썼다 — 나머지 네
모양으로 쓴 첫 시도는 처방을 빼도 통과했다(무의미한 테스트였다).

오늘 카탈로그 17개에는 함수형 의사클래스 안 콤마가 0건이고 `:not(`(10) ·
`:where(`(13) 만 있다. 3차의 주석 중괄호와 4차의 문자열 중괄호도 똑같이 0건이었고,
